### Что там уже решено за нас

- `@Mod` → `ModInitializer` + `ClientModInitializer`
- `DeferredRegister` для двух `Feature` → `Registry.register`
- **13 датапак-реестров** → Fabric `DynamicRegistries.register(...)` unsynced.
  Это ровно те реестры, которых нам не хватает (conditions, worldstyles, scattered,
  predefinedspheres), и решение уже написано и проверено.
- biome-modifier JSON (NeoForge) → `BiomeModifications.addFeature(BiomeSelectors.tag(
  BiomeTags.IS_OVERWORLD), RAW_GENERATION / TOP_LAYER_MODIFICATION, key)`
- `ModConfigSpec` → Forge Config API Port (fuzs), код конфига **не меняется вообще**
- `NeoForge.EVENT_BUS.post(LostCityEvent)` → `LostCityEvents` с пятью Fabric `Event<Consumer<>>`
- `ServerLifecycleHooks.getCurrentServer()` → свой `varia/ServerAccess`
- `Tags.Biomes.IS_VOID` → `c:is_void`
- `LevelEvent.CreateSpawnPosition` → миксин в `MinecraftServer#setInitialSpawn`
- Кнопка «Cities» в экране создания мира → `ScreenEvents.AFTER_INIT` + `Screens.getWidgets`
  (у нас уже сделано так же — коммит `3bc6e9f`)
- AccessTransformer → `.accesswidener` (6 записей, нужны для `NoiseChunkOpt`)
- Датаген выкинут, шесть JSON тегов блоков положены в jar готовыми

Плюс они нашли и исправили баг, **который есть и в оригинале, и почти наверняка у нас**:
один `LostCityTerrainFeature` с одним общим `ChunkDriver` на измерение + `setWorld()`
прямо перед генерацией = гонка при параллельной генерации чанков. Симптомы —
`Requested chunk unavailable`, NPE на `primer`/`region`, обращения за 3–8 чанков от региона.
У нас в `MULTIVERSION.md` `Requested chunk` упомянут как признак поломки, а в истории есть
коммит `2845f71` «fix: out-of-bounds chunk requests» — то есть мы лечили симптом.
Их лечение: `synchronized` на общем инстансе вокруг `setWorld` + генерации, плюс мягкое
клампование в `getBlockSafe`/`updateAdjacent`.

### Чего там нет

Ветка отпочковалась от `1.21.11_neo` @ `d2148510` — **до** того, как автор перенёс туда
иерархические улицы и межгородские шоссе. Сейчас `origin/1.21.11_neo` = `8859e3c3`
и содержит `worldgen/street/` и `worldgen/highway/` целиком. То есть Arilas показывает
*как* портировать, но их снапшот кода уже на 3 коммита устарел. Брать надо свежий
`1.21.11_neo`, а способ портирования — от них.

## Главный вывод: подход надо менять

Сейчас порт — переписывание с нуля: свой пакет `com.lostcity`, свои классы, своя
архитектура (`AssetLoader` вместо реестров, `ProfileConfig` вместо `LostCityProfile`).
10 888 строк написано вручную, и это ~45–50% мода.

Оставшиеся 50% — это `LostCityTerrainFeature` целиком, `DamageArea`, `Explosion`,
`CitySphere`, `Railway`, `Scattered`, `NoiseChunkOpt`, `worldgen/street/**`,
`worldgen/highway/**`, GUI, команды, API. Переписывать это руками — ещё примерно
16 тысяч строк. И каждый апстрим-коммит автора придётся переносить вручную,
переводя из его структуры в нашу. Это не сходится: автор коммитит быстрее.

Форк Arilas доказал, что есть путь дешевле на порядок: **взять исходники оригинала как
есть и заменить только связку с загрузчиком.** 200 строк правок в ядре против 16 тысяч
строк переписывания. И дальше апстрим прилетает через `git cherry-pick`, а не через
ручной перенос.

### Вариант A — продолжать переписывать

- Плюсы: не надо ломать то, что уже работает; нет зависимости от Forge Config API Port;
  свои имена классов.
- Минусы: ~16 тысяч строк ручной работы; 1:1 недостижимо в принципе, потому что
  «упрощённых версий» в `City.java`, `CompiledPalette`, `ChunkHeightmap` уже сейчас
  накопилось на расхождение в генерации; каждый апстрим-коммит — ручной перенос;
  сравнить свой код с оригиналом построчно нельзя.

### Вариант B — пересобрать порт на исходниках оригинала (рекомендую)

Взять `origin/1.21.11_neo` @ `8859e3c3` как основу, снять с неё NeoForge по рецепту
Arilas, натянуть Stonecutter на диапазон 1.20–1.21.11.

- Плюсы: настоящий 1:1, потому что это буквально тот же код; апстрим через `cherry-pick`;
  `git diff` против ветки автора как постоянная проверка полноты; сразу приезжают все
  отсутствующие подсистемы (повреждения, сферы, ж/д, scattered, иерархические улицы,
  шоссе, команды, GUI, API); мультиверсионность сохраняется — Stonecutter работает
  на любом коде.
- Минусы: надо один раз переделать проект; появляется зависимость Forge Config API Port
  (либо своя прослойка под `ModConfigSpec`, см. ниже); придётся перейти на Mojang-маппинги.

Оценка B: 3–5 недель плотной работы против 4–6 месяцев для A. И A не даёт 1:1.

## Три решения, которые надо принять до начала

### 1. Маппинги: Yarn → официальные Mojang

Код `mcjty.lostcities` написан под официальные имена (`BlockState`, `LevelAccessor`,
`RandomSource`, `ResourceLocation`). У нас Yarn (`BlockState`, `WorldAccess`, `Random`,
`Identifier`). Переводить 23 тысячи строк из Mojmap в Yarn — это и есть та ручная работа,
которую мы пытаемся не делать.

Loom поддерживает `loom.officialMojangMappings()` на всём диапазоне 1.20–1.21.11.
Переходим на них — и исходники оригинала компилируются почти как есть.

Стоимость: наши 10 888 строк придётся выкинуть или переписать. Но при варианте B их
и так заменяют исходники оригинала, так что это не дополнительная потеря.

Побочный плюс: диффы автора между его ветками (`1.20` ↔ `1.21_neo` ↔ `1.21.11_neo`)
станут применимы к нашему коду напрямую.

### 2. Конфиг: Forge Config API Port или своя прослойка

FCAP для Fabric есть на весь наш диапазон (1.20.1, 1.20.4, 1.20.6, 1.21.1, 1.21.4,
1.21.8, 1.21.11 — версии `v8.x` … `v21.11.x`). Если брать его, `setup/Config.java`
и `config/LostCityProfile.java` (795 строк, ~200 настроек) переносятся **без единой правки**.

Цена — жёсткая зависимость: игрок должен доставить ещё один мод.

Альтернатива: написать свою прослойку с API `ModConfigSpec` (`ConfigValue.get()`,
`Builder.comment().define*()`) поверх нашего `ConfigManager`. Это ~300–400 строк один раз,
зависимости нет, `LostCityProfile` по-прежнему переносится без правок.

Рекомендую **свою прослойку**: у порта сейчас нет hard-deps кроме Fabric API, и это
его преимущество на Modrinth. Но начать можно с FCAP, чтобы быстрее увидеть рабочую
сборку, и заменить его на прослойку на шаге 6.

### 3. Опорная ветка: `1.21.11_neo`, а не `1.20`

`origin/1.21.11_neo` @ `8859e3c3` и `origin/1.20` @ `14cfb810` — один набор фич
(216 и 220 файлов, уникальных всего 6 и 2). Разница между ними — 831/1038 строк в
106 файлах, и почти всё это загрузчик и `setup/`, которые мы всё равно заменяем.
В `worldgen/` дельта крошечная: `LostCityTerrainFeature` 41/34, `ChunkDriver` 34/9,
`BuildingInfo` 21/24.

Берём `1.21.11_neo` как основу, потому что она ближе к верху нашего диапазона и её
API новее. А `git diff origin/1.20 origin/1.21.11_neo` — это **готовая карта того,
что именно менялось в MC между 1.20.1 и 1.21.11 в этом конкретном коде**. Ровно те
места, где нужны условия Stonecutter. Автор сделал эту работу за нас, надо просто
прочитать дифф.

Прикидка: 106 файлов дельты, из них ~30 в `worldgen/`. Значит условий Stonecutter будет
не 3, как сейчас, а порядка 60–100. Это нормально и всё ещё поддерживаемо — это по-прежнему
один набор исходников, а не семь ветвей.

## Порядок работ

Каждый шаг заканчивается проверяемым результатом. Ветку `multiversion` не трогаем,
работаем в новой (`rebase-upstream`), чтобы в любой момент можно было откатиться
к тому, что уже работает.

### Шаг 0 — мелочи в текущей ветке (полдня)

Это надо сделать независимо от выбора варианта, потому что это живые баги.

1. Путь иконки в `fabric.mod.json`: `assets/lostcity/` → `assets/thelostcity/`
   (или переименовать каталог в `assets/lostcities/`, чтобы совпадало с `mod.id`).
2. `stonecutter registerChiseled tasks.register("buildAndCollect", stonecutter.chiseled)`
   в `stonecutter.gradle.kts` — иначе задача из `MULTIVERSION.md` не существует.
3. Убрать из `MULTIVERSION.md` раздел про удалённый `tools/check-mixin-targets.sh`.
4. Удалить `TODO_CHECKLIST.md` — он обрезан и устарел, его заменяют `PORT_AUDIT.md`
   и этот файл.

Тег на текущем состоянии, чтобы было куда вернуться.

### Шаг 1 — каркас (3–4 дня)

5. Новая ветка. Влить исходники `origin/1.21.11_neo` @ `8859e3c3` в `src/main/java`
   так, чтобы сохранилась история: добавить оригинал как remote и слить дерево, а не
   скопировать файлы. Тогда `cherry-pick` апстрима потом заработает.
6. Перевести Loom на `officialMojangMappings()` для всех 7 подпроектов.
7. Собрать под одну версию — **1.21.11**, она ближе всего к базе. Цель шага:
   `:1.21.11:compileJava` зелёный. Ориентир по правкам — 73 изменённых файла Arilas.
8. Порядок внутри шага (их нумерация WS, чтобы можно было сверяться с их заметками):
   точка входа и жизненный цикл → регистрация двух `Feature` → 13 датапак-реестров →
   внедрение фич через `BiomeModifications` → конфиг → сеть → события API →
   шимы (`ServerAccess`, `LostTags.IS_VOID`) → access widener → миксин точки спавна →
   клиентский GUI.
9. Взять их фикс потокобезопасности целиком (`synchronized` вокруг `setWorld` +
   генерации, мягкое клампование в `ChunkDriver`). Не откладывать — без него краши
   при генерации спавна.

Результат: `:1.21.11:runServer` стартует, мир генерируется, города есть.

### Шаг 2 — вниз по диапазону через Stonecutter (1–1.5 недели)

10. Распечатать `git diff origin/1.20 origin/1.21.11_neo -- src/main/java` и разобрать
    как список задач: каждое расхождение — либо одинаковый для всех версий API,
    либо условие `//? if >=x.y`.
11. Порядок добавления версий: 1.21.8 → 1.21.4 → 1.21.1 → 1.20.6 → 1.20.4 → 1.20.1.
    Сверху вниз, потому что соседние версии отличаются меньше всего.
12. Правило прежнее и оно себя оправдало: где есть API с одинаковой подписью во всех
    версиях — использовать его, а не ветвиться. Условие Stonecutter — последнее средство.
13. Отдельно посмотреть `NoiseChunkOpt` / `HeightGenOpt` (962 + N строк): они
    переписывают внутренности ванильного `NoiseChunk`, и это самое версионно-хрупкое
    место во всём моде. У Arilas оно помечено как «runtime не проверен».
    Вариант: включать оптимизированный путь только на тех версиях, где он проверен,
    а на остальных отдавать ванильный (в оригинале это уже флаг
    `optimizedHeightmap`, по умолчанию `false`).

Результат: 7 джарников собираются, каждый стартует на сервере и клиенте.

### Шаг 3 — проверка равенства оригиналу (1 неделя)

14. Сверка генерации: один сид, один профиль, оригинал на Forge 1.20.1 и наш джарник
    на Fabric 1.20.1 — сравнить скриншоты и структуру нескольких чанков.
    Разметка городов от сида не зависит (это уже проверено в `MULTIVERSION.md`),
    поэтому расхождения должны быть только от ванильного шума рельефа.
15. Пройти их список «Things to test in-game»: кнопка Cities и GUI профиля, генерация
    на `default`/`rarecities`/`biosphere`, датапак-измерение `lostcities:lostcity`,
    команды (`map`, `locate`, `debug`, `editmode`), телепорт-кровать, точка спавна
    с `SPAWN_BIOME`/`SPAWN_CITY`/`FORCE_SPAWN_IN_BUILDING`.
16. Известные проблемы, которые приедут вместе с оригиналом и которые надо решить
    у себя, а не ждать автора:
    - невалидный `selectedProfile` крашит инициализацию мира в
      `Config.getProfileForDimension` (баг есть и на NeoForge);
    - `lostcities/stuff/example.json` ссылается на несуществующий `#forge:stone`;
    - IMC-интеграции с другими модами McJty на Fabric не заработают в принципе.

### Шаг 4 — убрать зависимость от Forge Config API Port (3–4 дня, опционально)

17. Написать прослойку с API `ModConfigSpec` поверх своего `ConfigManager`.
    `setup/Config.java` и `config/LostCityProfile.java` остаются без правок.
18. Убрать FCAP из `fabric.mod.json` и `build.gradle.kts`.

### Шаг 5 — процесс поддержки (постоянно)

19. Оригинал как remote, ветка автора как эталон. Регулярно
    `git log ..origin/1.21.11_neo` и `cherry-pick` новых коммитов.
    Конфликты будут только в тех 73 файлах, которые мы адаптировали.
20. В CI собирать все 7 версий на каждый пуш. Сейчас в `.github/` есть workflow —
    проверить, что он покрывает все версии, а не одну.
21. `git diff` против ветки автора по `worldgen/` — постоянный индикатор полноты порта.
    Пока он пустой (кроме версионных условий) — порт равен оригиналу.

## Если всё-таки вариант A

Тогда порядок из `PORT_AUDIT.md` («Порядок работ», шаги 1–5) остаётся в силе,
но форк Arilas всё равно надо держать открытым: их `PORTING-NOTES.md` — это готовые
ответы на «как это сделать на Fabric» для реестров, событий, конфига, точки спавна
и GUI. И фикс потокобезопасности надо забрать в любом случае, он не зависит от подхода.

Даже в варианте A я бы забрал из оригинала целиком, не переписывая, четыре куска —
они почти не трогают загрузчик, а у нас их нет совсем:
`lost/DamageArea.java`, `lost/Explosion.java`, `lost/Railway.java`, `gen/Scattered.java`.
Перевод из Mojmap в Yarn для них — механическая работа на день, а не переписывание.
